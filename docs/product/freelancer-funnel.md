# Freelancer / Solo-Builder Funnel

Workflow OS first serves a **solo service-and-product delivery business**, not a SaaS growth funnel for Workflow OS itself.

The operator may receive a client request, identify a user problem, or start an internal product idea. The funnel should support websites, mobile/SaaS products, automations/integrations, data systems, and future client-facing AI Employees without forcing every engagement into an automation-only shape.

```text
Lead / User Problem / Product Idea
 -> Problem Audit / Intake
 -> Research + Feasibility + Risk
 -> Paid Discovery / Project Blueprint (for client work)
 -> Smallest Valuable Pilot / MVP
 -> Independent Verification / Acceptance
 -> Production Deployment
 -> Managed Maintenance / Retainer or Internal Operations
 -> Expansion / Additional Features or Workflows
 -> Reusable Client-Neutral Pattern
```

## Intake inputs

Depending on the Project, capture:

- user/business problem;
- desired outcome;
- current process/system;
- target users/stakeholders;
- frequency/volume/scale where relevant;
- systems/data/integrations;
- rules/exceptions/approvals;
- business impact;
- time/error/rework baseline;
- security/compliance constraints;
- budget/deadline/operational constraints;
- what success would look like.

The output is a prioritized Project/problem definition, not a promise to build or automate everything requested.

## Discovery / blueprint outputs

As applicable:

- evidence/research and open questions;
- as-is process/system;
- target user/problem/outcome;
- scope and explicit non-goals;
- requirements/acceptance criteria;
- solution/architecture recommendation;
- workflow/automation opportunities;
- systems/interfaces/data model;
- rules/exceptions/approval model;
- feasibility/risk/security/reliability assessment;
- ROI/value estimate where meaningful;
- work graph / pilot plan;
- verification and deployment plan;
- maintenance/ownership expectations.

## Pilot / MVP selection

Prefer the smallest slice that proves real user/business value and the riskiest important assumption without requiring speculative scale infrastructure.

For automation-heavy work, prefer a process that is frequent, measurable, bounded, reversible, low-to-medium risk, and supported by stable interfaces.

For software/product work, prefer a thin vertical slice that exercises the critical user path end-to-end and can be independently verified.

## Delivery evidence

A pilot is not complete merely because code or a workflow exists. Require the risk-appropriate evidence from `docs/engineering/agent-operability-and-verification.md` and applicable workflow testing contracts.

## Maintenance / retainer value

Depending on the Project:

- monitoring and incident triage;
- bug fixes and regression tests;
- provider/API/dependency changes;
- workflow/product optimization;
- deployment/rollback support;
- agreed credential-rotation coordination;
- security/runtime updates;
- monthly health/ROI reporting;
- documentation updates;
- agreed feature/workflow allowance.

Maintenance state should remain visible through the Project Command Center rather than live only in messages/reminders.

## Productization loop

Every successful Project should be reviewed for reusable, client-neutral patterns:

- Project templates;
- research/requirements checklists;
- architecture patterns;
- Skills/workflows;
- agent verification maps;
- test/eval cases;
- deployment/maintenance runbooks;
- future client-facing AI Employee templates.

Reuse logic, structure, and sanitized lessons. Never template confidential client material, secrets, or proprietary assumptions.
